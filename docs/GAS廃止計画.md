## ★課題1：スプレッドシート → サイトへのデータ反映をどうするか★

### 何が問題か

現在、施設データは2か所にあります。

| 場所 | 件数 | 役割 |
|---|---|---|
| スプレッドシートv12 | 200行超 × 43列 | **Kenjiさんが入力する正本** |
| `ランキング/index.html` の `FACILITIES` | 176件 × 11項目 | **サイトが表示に使うスナップショット** |

**スプレッドシートを更新しても、サイトには自動反映されません。**
GASが無くなると、この橋渡しをする仕組みが必要になります。

### 選択肢

| 案 | 方法 | 長所 | 短所 |
|---|---|---|---|
| **A（推奨）** | Kenjiさんがスプレッドシートを **CSVでダウンロード** → リポジトリに置く → スクリプトが `FACILITIES` を更新 | 認証不要・仕組みが単純・壊れにくい | ダウンロード操作が毎回必要 |
| **B** | スプレッドシートを **「ウェブに公開」** してCSV URLを取得 → AIエージェントがそのURLを読む | Kenjiさんの操作が減る | **スプレッドシートの内容が公開URLになる**（誰でも見られる） |
| **C** | AIエージェントが **Google Drive連携で直接読む** | 操作が一番少ない | エージェントにDrive接続が必要。Codexでは使えない可能性 |
| **D** | GitHub Actions + Google Sheets API で自動同期 | 完全自動 | サービスアカウントの設定が必要。Kenjiさんには複雑すぎる |

### 推奨：案A（CSVを置く方式）

理由：
- **Kenjiさんはプログラミング初心者。** 認証情報の設定が要らない方式が安全
- どのAIエージェント（Claude Code / Codex / 将来の何か）でも同じように使える
- リポジトリにCSVが残るので、**データの履歴がGitで追える**（いつ何が変わったか分かる）

**Kenjiさんの操作は3ステップだけ：**
1. スプレッドシートで「ファイル」→「ダウンロード」→「カンマ区切り形式（.csv）」
2. そのCSVをAIエージェントに渡す（またはリポジトリの `data/` に置く）
3. 「サイトに反映して」と頼む

エージェント側は `scripts/` に変換スクリプトを1本作れば、あとは実行するだけになります。

> **⚠️ この案はまだKenjiさんの承認を得ていません。** 実装前に確認してください。
> 案Bを選ぶ場合は「スプレッドシートの中身が全世界に公開されてよいか」を必ず確認すること。

## ★課題2：マップ機能をどうするか★

GASの `?page=map` にあるマップ機能（Leaflet + OpenStreetMap、13種フィルター、
都道府県タイル＋ピンマップ）は、**静的サイトに存在しません。**

**GASを廃止すると、この機能は失われます。**

### 選択肢

| 案 | 内容 | 手間 |
|---|---|---|
| **A** | 静的ページとして作り直す（LeafletはCDNから読めるので静的サイトでも動く） | 中〜大 |
| **B** | いったん諦める。将来やる | なし |

**技術的には案Aは十分可能です。** Leafletは外部CDNから読み込めば静的HTMLで動作し、
施設データ（座標込み）をJSONで持たせればフィルターも実装できます。

ただし現状、**マップはサイトのメニューからリンクされていません**
（ナビは トップ/WHY/ランキング/サウナ大学/お問い合わせ/サイトマップ）。
つまり **今の訪問者はマップを見ていない可能性が高い** ため、
移行の優先度は低いと判断できます。

> **要確認**：マップは公開されていたのか、それとも作ったまま未公開だったのか。
> 未公開なら、移行を急ぐ必要はありません。

## 廃止の手順（推奨する順番）

**焦らないこと。動くものを止めるのは一番最後です。**

### ステップ1：GitHub Pagesでサイトを公開する
→ `docs/GitHub-Pages移行手順.md` に従う。まずサイトが新しい場所で動くことを確認。

### ステップ2：データ反映の仕組みを作る（課題1）
Kenjiさんと方式を決めて、`scripts/` に変換スクリプトを作る。
一度スプレッドシートの最新版で `FACILITIES` を更新し、
**サイトの数字がスプレッドシートと一致することを確認する。**

### ステップ3：記事生成・校閲をAIエージェントに移す
GASのプロンプト（しきじ版文体＋SUSURUルール）は
`docs/記事執筆ルール.md` に文書化済み。エージェントはこれを読めば同じ品質で書ける。

**次に記事を1本書くときに、GASを使わずエージェントだけで書いてみて、
品質が落ちないか確認する。** これが確認できたらGASの記事機能は不要になる。

### ステップ4：マップの扱いを決める（課題2）

### ステップ5：WordPressを止める
→ `docs/GitHub-Pages移行手順.md` のステップ7

### ステップ6：GASを止める

**止める前に必ずやること：**

- [ ] GASのソースコード全文を**バックアップとしてこのリポジトリに保存する**
      （`archive/gas/` のようなフォルダを作る。将来「あの処理どうやってたっけ」となるため）
- [ ] スクリプトプロパティに入っている鍵の扱いを決める
      - `ANTHROPIC_KEY` … GASを止めるなら**Anthropicのコンソールで無効化**する
      - `WP_USER` / `WP_APP_PASS` … WordPress廃止と同時に無効化
- [ ] スプレッドシートに付いているGASのトリガー（時間主導型など）があれば削除
- [ ] デプロイを「アーカイブ」する（いきなり削除せず、しばらく残して様子を見る）

> **⚠️ 重要：GASのソースコードをリポジトリに保存する場合、
> ファイルIDやデプロイURLなどが含まれていないか必ず確認してから保存してください。**
> このリポジトリは公開になる可能性があります（→ `docs/GitHub-Pages移行手順.md` の警告参照）。

## 廃止後に「できなくなること」の一覧

Kenjiさんが後で困らないよう、正直に書いておきます。

| できなくなること | 代わりの方法 |
|---|---|
| スマホの編集アプリで施設データを直接編集する | **スプレッドシートを直接編集する**（スマホのGoogleスプレッドシートアプリで可能） |
| ボタン1つで記事の下書きを生成する | **AIエージェントに「〇〇の記事を書いて」と頼む** |
| ボタン1つで校閲する | **AIエージェントに「この記事を校閲して」と頼む** |
| マップを見る | 課題2の判断次第 |
| スプレッドシートの更新が自動でサイトに出る | 課題1の仕組み次第（案Aなら「反映して」と頼む一手間が入る） |

**逆に、良くなること：**

- サーバー代（ConoHa）が不要になる
- 「GASを再デプロイする」という作業が消える（過去に25回以上の無駄なデプロイで消耗した経緯あり）
- WordPressの管理画面・プラグイン・WAFのトラブルから解放される
- 変更履歴がすべてGitに残る（何をいつ変えたか追える）
- サイトの表示が速くなる（iframeが無くなり、静的ファイルだけになる）
